# Account database regressions

Run `pnpm install --frozen-lockfile` and `pnpm test` from this directory. PGlite 0.5.8 is pinned with an integrity lockfile. It executes PostgreSQL functions, triggers, RLS, constraints, role changes, and transactions locally. No production connection, credentials, Docker, or message delivery service is used.

The production-shaped fixture contains the tables and existing rules needed for these repairs, including broad Supabase-style default table grants and the Realtime publication. The profile SELECT rule is deliberately simplified; this suite does not replace the separate production profile/privacy policy audit. Private demographic and complimentary billing records remain unchanged by the migration. Each test runs in a rolled-back transaction.

The suite verifies café completion, blank fields, suspension, visibility opt-outs, email and role-less OAuth signup, direct API authorization and immutable application identity, supported status transitions, complete Florida job addresses and legacy updates, durable discovery notifications, recipient-scoped read acknowledgments, unrelated/blocked/anonymous denial, and privileged helper permissions.

## Release order and recovery

Applied to the production database on 7 September 2026 as version `20260907050656`. Read-only verification confirmed the complete-café predicate, application initial-status check, new table/RPC privileges and Realtime registration. Security advisors returned no findings. Profile visibility and job-active fingerprints were identical before and after the migration; no member or job state was republished.

Apply `20260907050656_repair_account_integrity_and_discovery_notifications.sql` before deploying the frontend that reads `discovery_message_notifications` and calls `mark_discovery_conversation_read(p_match_id)`. The RPC is a security invoker and returns an integer count; the notification trigger resides in `private` and is not client-callable. The new table has only `id`, `recipient_id`, `discovery_match_id`, `created_at`, and `read_at`. The authenticated role can SELECT its own rows and UPDATE only `read_at`; direct INSERT, DELETE, identity changes, anonymous access, and service-role inserts are revoked. Only the private trigger creates these events. The table is added to an existing `supabase_realtime` publication once.

Existing `notifications` schema and application events remain untouched, so shipped native apps do not gain discovery badges they cannot acknowledge. Existing discovery messages are not retrospectively marked unread. The frontend must subscribe to the new recipient-scoped table and refresh an active discovery conversation on its events; the production publication previously contained `messages` and `notifications`, not `discovery_messages`. Billing access policies remain unchanged.

The migration does **not** flip any profile's visibility flag. An existing café owner should reopen and save their completed Café Profile. The corrected database predicate then accepts their explicit publish action; the frontend must use the saved database row before reporting success. Existing barista `visible_to_cafes` opt-ins remain untouched. A support-assisted recovery may first select which cafés satisfy the new predicate, but any bulk publication should be a separate reviewed decision.

New applications must start `interested`. Only the owning café may change `interested` to `matched` or `declined`; the applicant may withdraw an `interested` or `matched` application. Terminal applications cannot be silently reopened. Existing records are not reclassified. Trusted service-role administration remains possible.

New or revised job addresses must contain a street, city, `FL`, and a five-digit or ZIP+4 postal code. Unchanged legacy addresses remain compatible with ordinary title/description/pause updates. Updating one address field on a legacy row requires supplying a complete address. No existing job location is rewritten by migration application.

After production application, run security advisors, confirm migration presence and new table/RPC privileges, and query a synthetic complete café composite through `profile_meets_visibility_requirements` (SELECT only). Complete real role-to-role smoke tests using authorized test accounts. Roll back the frontend independently if needed; preserve the authorization repairs and resolve database problems with a reviewed forward migration.

## Account policy performance migration

`20260907061824_optimize_account_policy_auth_checks.sql` adds the missing `discovery_messages(sender_id)` foreign-key index and wraps `auth.uid()` in a scalar `SELECT` in eight existing simple ownership policies. `ALTER POLICY` keeps policy names, roles, commands, permissive mode and predicate meaning. Both complimentary-access write policies, table/column grants, private demographics, profile visibility, existing indexes and user records remain unchanged. A local three-second lock timeout makes index creation fail promptly if the table is busy; retry during a quiet period instead of waiting behind active writes. This is a transactional migration, so it intentionally uses ordinary index creation. The tested migration was applied to the linked production project on September 7, 2026 and recorded in its migration history as `20260907061824`. Post-apply security advisors reported no findings and performance advisors reported no warnings.

The separate `policy-performance.test.mjs` suite loads `policy-performance-fixture.sql` into a fresh PGlite instance using synthetic accounts and production policy definitions captured read-only on 2026-09-07. It proves unchanged policy/grant metadata, own-account reads and writes, cross-account/null-session/anonymous denial, preserved billing restrictions, statement-scoped identity refresh, an actual PostgreSQL InitPlan, index use and unchanged foreign-key cascade behavior. The fixture includes only the columns needed to exercise these policies; it is not a full production schema dump or a timing benchmark. Run both database suites with `node --test tests/database/*.test.mjs` from the repository root.

## Website abuse budgets and client privilege hardening

`public-form-budget.test.mjs` runs the durable website budget migration in PGlite. It checks service-only execution, private default-deny RLS, strict hashed-input bounds, exact request caps, all-or-none denial, expiry reset, and bounded cleanup. `client-privilege-hardening.test.mjs` executes actual client TRUNCATE denials while preserving ordinary row-level CRUD, policies, service maintenance privileges, and existing client RPC grants. These migrations do not change native source, review state, or existing billing rules.

PGlite has one backend; its overlapping JavaScript promises do not prove independent-session locking. The required website security CI therefore runs `public-form-budget-postgres.test.mjs` against a disposable PostgreSQL 17 service using the runner's `psql` client. That suite races independent sessions with reversed and overlapping keys, verifies a single expiry reset, checks that rejected recipients leave no counters, holds a real row lock while cleanup uses `SKIP LOCKED`, and verifies the function's one-second lock timeout rolls back earlier writes. It also confirms actual PostgreSQL ownership, RLS, `search_path`, and role grants.

To run that opt-in suite, provide `BJM_TEST_DATABASE_URL` for a fresh, disposable local PostgreSQL 17 database named exactly `bjm_security_test`, using the `postgres` user, then run `node --test tests/database/public-form-budget-postgres.test.mjs`. The connection guard accepts only loopback hosts, pins libpq's host address to loopback, rejects connection-option overrides and other database names, and refuses to initialize a database containing existing user tables. Never point it at a hosted project, production tunnel, or an application database. Without that variable, only its connection-guard test runs; the seven database integration tests explicitly skip. No production credentials are required.

Apply `20261021133639_add_durable_public_form_budgets.sql` before deploying the website guards. Deploying guarded endpoints without their RPC fails closed with a service-unavailable response. Use a reviewed forward migration for database recovery; the website and database rollout remain separate from iOS builds or App Review.
